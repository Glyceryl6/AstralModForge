# 星航 MOD 工坊 v0.2.0 · 架构与限制 / Architecture & limitations

## Rider 前端与 Java 导出核心

Rider 的 C# 语义服务主要在 ReSharper 后端，当前工具只实现 Java/IntelliJ 前端，并不具备完全准确的 C# 调用图。`CSharpIndex` 采用源码索引、类型名称与标识符启发式分析；`ClassSelectionModel` 用索引得出的关系构造勾选图；`DependencyPlanner` 再次计算闭包并选择初始化入口。两次检查只提高可预见性，不等同于 Roslyn 语义分析。

**选中是用户要启动的功能集合；依赖是为编译所需的闭包。** 只有明确选中的功能类才自动推断启动入口，依赖类不会自动执行其自己的 `Init`、`Tick`。缺失入口、反射调用、类名冲突、泛型、IL2CPP 注册和 Harmony 钩子仍需开发者单独确认。

## 模块职责

| Java 文件 | 作用 |
|---|---|
| `CSharpIndex` | C# 文本索引、类型与可见文件关系；排除同名私有嵌套类型误匹配 |
| `ClassSelectionModel` | 勾选时求下游依赖闭包，取消时撤销反向依赖它的已选根功能 |
| `ClassSelectionTree` | Swing `JTree` 层级目录、可展开文件、复选框与部分勾选 |
| `DependencyPlanner` | 依赖补齐、`partial` 分部、Load/Update 入口选择、预检报告 |
| `SettingsDetacher` | 识别原宿主 `ConfigEntry<bool>` 的 `.Value` 只读引用，固定为 `true`，剔除设置相关 `using`；拒绝危险引用 |
| `LocalizationTransformer` | 生成独立语言字典或仅安全内联明确的翻译键 |
| `ForgeSpec` | 校验 MOD ID、导出模式、游戏目录、源码路径边界 |
| `ForgeExporter` | 创建临时／永久工程、流式 `dotnet` 日志、构建、可选部署、生成报告、清理临时目录 |
| `ExportObserver` | 构建阶段、流式日志与取消信号，界面和核心之间的无 IDE 依赖接口 |
| `BuildLogService` | Rider 项目级构建日志服务，按 JetBrains 规定标为 `final` |
| `ForgeToolWindowFactory` | 下方日志窗口，配合深浅主题 SVG 图标 |
| `I18n` | JetBrains `DynamicBundle`，根据 IDE 语言选用中英文 Properties |
| `cli.Main` | 与 Rider UI 复用同一个核心引擎 |

## 设置拆分安全策略

1. 不复制宿主 `Plugin.cs`、`HotfixWatcher.cs`、`Framework.Settings`、`Framework.Configuration` 和原 `ModLanguageService`。这些类型与原设置页及初始化生命周期耦合，不属于独立功能的普通编译依赖。
2. 只对宿主声明能确认的 `ConfigEntry<bool>` 或 `ConfigEntry<Boolean>` 读取 `Plugin.Name.Value`、`SomethingConfiguration.Name.Value` 改写为 `true`。支持常见表达式体转发属性。`ConfigEntry<int>`、`<float>`、`<string>` 等值并不能无损转换为“始终开启”，故报错。
3. 如果代码写入 `.Value`、通过 `ref/out` 引用，或将原 `ConfigEntry` 对象直接传给方法，拒绝自动转换。识别不到成员类型、遗留无法隔离的原配置类引用时，同样阻止导出。
4. 此策略不修改原 MOD 源文件，也不为生成 MOD 增加任何来自原设置页面的开关或旧配置值。
5. **注意边界**：因为是文本启发式解析，某些别名、扩展方法、重载、局部同名类型仍可能无法正确识别；必须做编译、运行验证，特别是原项目配置类层次复杂时。

## 路径与源代码冲突

`ForgeSpec.exportSource=false`（Rider 默认）时，完整 C# 工程构建在 OS 临时目录，仅保留必要输出，结束后清理。`exportSource=true` 时，默认目标为源工程同级 `<root>-ForgeExports`。禁止将源码输出到源工程根目录或其子目录，避免 `.csproj` 隐式 `Compile Include="**/*.cs"` 和同名 `Plugin` 导致类型重复定义；特殊的非 SDK 工程请自行审查其 `.csproj` 包含规则。

无 DLL 时不可部署，部署路径要通过游戏/BepInEx 验证；已有 DLL 先备份。不要让原 MOD 与独立 MOD 在同一游戏会话中重复启用同一功能，以免重复事件订阅、重复 UI 或热键冲突。

## 构建／取消／报告

默认 `dotnet build` 使用 Release、`net6.0`，输出逐行写入 `build.log` 和 UI `BuildLogService`。额外生成 `export-manifest.properties`（所需文件、语言模式、启动入口、源码输出选项）及 `export-report.md`。构建失败不能伪装成功，禁止部署；超时或取消尝试终止子进程并保留日志。

`dotnet build` 只能检查可编译性，不能验证 Unity/IL2CPP 的实时注册、原 MOD 生命周期或游戏内效果。导出源项目对 SDK 的引用可能使用机器上的绝对路径，跨设备移植时需修复 `ProjectReference` / NuGet 配置。

## IDE 与打包限制

- 插件主体是 Java 21，Gradle 使用 `org.jetbrains.intellij.platform` **2.20.0**、Rider **2025.2.3**、Gradle **9.0.0+**。
- JetBrains 对 `@Service` 轻量服务明确要求 `final`，所以 `BuildLogService` 保留 `final`；普通类则没有无意义的 `final` 和空私有构造函数。
- 打包候选包可离线编译 Java 代码，但若没有真实 JetBrains SDK，就不能证明 API 二进制兼容、插件启动、UI 行为或 `buildPlugin` 成功。正式发布必须在联网 IDE 中构建，并在对应 Rider 上安装／试运行。
- `Messages.properties` 与 `Messages_zh_CN.properties` 对照 IDE 语言（不是操作系统语言）。构建日志、导出器诊断仍可能采用双语保底文字。
- 建议后续接入 Roslyn / ReSharper 伴生后端改善实际语义引用，不在当前版本凭空声称已实现完整 C# 调用链。
