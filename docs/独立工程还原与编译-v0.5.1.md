# Astral Mod Forge v0.5.1 — 独立工程还原与编译

## 一、问题背景

v0.5.0 只将宿主 `.csproj` 中的 NuGet 引用复制到生成工程，未附带 `NuGet.Config`。原 AstralProbe 使用了 BepInEx 官方包仓库；因此在只有 nuget.org 和 Microsoft Visual Studio Offline Packages 的环境下，`BepInEx.PluginInfoProps` 可能引发 `NU1101`。这个包是用于生成宿主 PluginInfo 的构建扩展，生成的独立 MOD 已经有 `[BepInPlugin]`，所以现在直接跳过该包。

另一个根因是原 AstralProbe 的 `Directory.Build.targets` 会从 `BepInEx/interop` 添加 Unity 模块、`Il2Cppmscorlib` 和游戏代理程序集的编译引用。把 `.csproj` 的 `PackageReference` 复制过去，并不等于复制了这些引用；Rider 仍会把部分 C# 类型标红。

## 二、导出工程的新文件

| 文件／目录 | 用途 |
| --- | --- |
| `MOD.csproj` | 独立的 .NET 6 C# 工程，含 NuGet、互操作 DLL 和 SDK 引用 |
| `NuGet.Config` | 显式配置 nuget.org、BepInEx 官方源和原工程声明的附加 HTTPS 包源（不复制凭据） |
| `ForgePaths.props` | 记录并允许修改 `ForgeInteropDir` 的本地路径 |
| `Dependencies/Projects/` | 所需 SDK C# 项目副本，使用相对 `ProjectReference`；不直接编入主 MOD DLL |
| `Source/` | 用户所选功能与必要依赖（仅勾选“导出源码”时保留） |
| `build.log` | NuGet restore 与 C# build 逐步输出（只有启用编译时） |
| `export-report.md` | 导出详情、引用说明和失败诊断 |
| `dist/<ModId>.dll` | **仅在编译成功时存在** |

## 三、在 Rider 中修复引用

1. 确认已安装 `.NET` SDK，命令行执行 `dotnet --info`。
2. 启动一次已安装 BepInEx IL2CPP 的游戏，使 `BepInEx/interop` 目录包含 `Il2Cppmscorlib.dll`、`UnityEngine.CoreModule.dll` 和 `UnityEngine.InputLegacyModule.dll`。
3. 打开**导出工程**下的 `ForgePaths.props`，检查 `ForgeInteropDir` 是否指向该游戏的 `BepInEx/interop`，不是原热更新源码目录，也不是游戏的 `_Data/Managed`。
4. 若原电脑上游戏目录被移动，修改 `ForgePaths.props` 中的路径，或设置环境变量 `ASTRAL_PARTY_INTEROP_DIR`；也可以在导出前填写插件界面的游戏目录（即使不勾选复制游戏）。
5. 在生成工程根目录执行：

```powershell
dotnet restore .\MOD.csproj --configfile .\NuGet.Config
dotnet build .\MOD.csproj -c Release --no-restore
```

6. 在 Rider 中重新加载 C# 项目／解决方案，等待 NuGet 还原与索引完成。文件仍然标红时，以 `dotnet build` 的第一条 `CSxxxx` 编译错误为准；不是所有问题都属于缺少包或代理 DLL。

`ForgePaths.props` 不包含游戏 DLL 本身。独立工程只能通过该目录读取游戏代理文件，不能在其他电脑上无条件直接构建；移动工程后可重新指定路径。游戏代理引用设置了 `Private=false`，不会随导出的 MOD DLL 一起复制。

## 四、NuGet 无法访问时

- 本次已自动提供 `https://nuget.bepinex.dev/v3/index.json` 和 `https://api.nuget.org/v3/index.json`。
- 如果网络、代理或公司镜像限制了访问，可修改导出工程的 `NuGet.Config` 为可用的包源；不要把私有源密码提交进 Git。
- 区分 `NU1101`（包不存在于可访问的源）与 `NU1301`（无法连接到源）。已缓存或已恢复的包也依赖正确的项目引用。
- 不建议为了绕过 `NU1101` 而删除所有 `BepInEx` / `SNWCreations` 包；这会造成新的 C# 引用错误。`SNWCreations.Il2CppInterop.*` 与源 MOD 的 HybridCLR 兼容版本应保持一致。

## 五、关于“导出成功但没有 DLL”

- 若取消“编译”，仅导出源码属于正常流程，不会产生 DLL。
- 若勾选“编译”，从 v0.5.1 起，还原失败、编译失败、缺少 .NET SDK、找不到游戏代理或缺少输出 DLL 均会返回错误；**不会再显示为完整导出成功**。
- 如果选择保留源码，仍可在导出目录查看/修改 `.csproj` 再重新编译。
- 如果没有勾选保留源码，临时源码目录会在失败后清理，但 `build.log` 与 `export-report.md` 会保留在导出结果目录。
- 只有 DLL 真正生成，才会允许复制到游戏目录；已有的 DLL 不会因为失败而被覆盖。

## 六、仍需注意

当前静态依赖分析与方法裁剪还不是完整的 C# 语义编译器。复杂静态初始化、反射、Harmony、游戏热更新类型和多项目特殊构建步骤仍可能在实际编译时产生错误。此时请查看 `build.log` 的首条 C# 编译错误，必要时回到原项目检查引用或导出入口。真实的 Rider SDK 插件包仍应由 GitHub Actions 进行构建，不使用模拟 IDE API 生成可安装插件。
