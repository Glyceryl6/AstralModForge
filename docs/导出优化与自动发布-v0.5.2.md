# Astral Mod Forge v0.5.2 · 导出优化与自动发布

## 1. 语言资源裁剪

- 选择 `UniversalTargetMarksService` 时，导出器只分析真正随功能进入独立工程的 C# 源文件。
- `ModLocalization.Translate("astralprobe.foo")` 等固定键会重新映射为独立 MOD 键；`Translate(choice.NameKey)` 可从本类的 `new(..., "astralprobe.xxx", ...)` 列表收集对应键。
- 对于 `Translate("astralprobe.stats." + name)`，按明确前缀选择键；未限定前缀的动态运行时键无法可靠推断，将在预检查阶段给出错误，而不是打包所有模块的 JSON。
- **显式补充动态键**：如确实需要，在原工程（包含 `.csproj` 的根目录）建立 UTF-8 文件 `localization-keys.txt`，例如：

```text
# 每行一个键，或以 .* 结束的前缀
astralprobe.chat.unread
astralprobe.addon.target_mark.*
```

导出器只会包含该清单匹配的词典条目，并且检查中英文是否都存在。此清单用于无法进一步确定来源的动态调用；不要把所有通用语言键写进去。导出报告会记录两种语言各自的键数。

**局限**：本功能是静态源码分析，不等同于完整 Roslyn 语义分析。反射、委托或运行时生成的键，需要开发者在清单中明确声明；错误的缺项不会自动猜测或加载全词典。

## 2. DLL 命名

`dev.astral.my-mod` 会输出 `Dev.Astral.MyMod.dll`。BepInEx 的插件 ID 仍是用户输入的 `dev.astral.my-mod`，源码文件夹及 C# 命名空间仍采用兼容旧版本的安全命名。源码工程的 `<AssemblyName>`、编译产物检查以及 `dist` 复制规则同步使用新名称。

**注意**：如果以前已经部署了下划线命名的旧 DLL，升级时应先备份并手动删除旧 DLL，否则可能同时加载两个版本。工具不会自动删除原文件。

## 3. Rider 右键操作

在 **Project 项目树**选中一个或多个 `.cs` 文件，或者在 **Editor 编辑器**中右键当前 C# 文件，选择 **“导出选中的 C# 类” / “Export Selected C# Classes”**。导出窗口会预先选中相应文件及其依赖。其他类型文件的右键菜单不显示该动作。Tools → Astral Mod Forge 中的新建/导出功能保持原状。

## 4. GitHub 自动构建与 Release

1. 将 **`AstralModForge-v0.5.2` 目录里面的内容**放到 GitHub 仓库根目录。尤其要保证 `.github/workflows/ci.yml` 位于仓库根目录，不是压缩包外层子目录。
2. 确认仓库 **Settings → Actions → General** 已允许 Actions 和需要的第三方 Action；检查 Actions 工作流是否被禁用。
3. 将改动推送到分支：`push`、`pull_request` 和 Actions 页手动 `Run workflow` 都能触发真实 Rider SDK 构建，生成可在 Actions Artifacts 下载的安装包与 CLI JAR。
4. 发布新版本时，更新 `gradle.properties` 的 `modForgeVersion`、`plugin.xml` 的版本、README 的当前版本，并创建 `.github/release-notes/vX.Y.Z.md`。请在仓库**实际默认分支**上合并这些改动。构建通过后自动创建 `vX.Y.Z` Release，正文采用版本说明文件，附件包含安装 ZIP、CLI JAR 和 SHA256 清单。
5. 如果已经存在同名 Release，工作流不会覆盖它。需要发布修复请提升版本号；如果仅存在同名标签，该标签必须指向本次通过验证的提交。

**排查“没有触发”**：看提交的分支和 `.github/workflows/ci.yml` 是否位于根目录；到 Actions 页检查工作流是否被禁用；如需发布，确认提交在默认分支。**排查“构建失败”**：查看 build 作业中 `Gradle` / `buildPlugin` 的日志，检查真实 Rider SDK 是否成功下载。**排查“构建成功但没有 Release”**：确认版本号已增加、release-notes 文件存在、release 作业未被跳过，以及仓库策略允许 `GITHUB_TOKEN` 创建 Release；如需要，在 Settings → Actions → General 检查工作流权限。项目无法在本地代为更改这些 GitHub 设置。

> 默认分支仍须具有有效的 Actions 工作流；GitHub Releases 面向公开仓库的访客可直接下载附件。本地离线测试不能验证 GitHub 实际权限及平台构建结果。
